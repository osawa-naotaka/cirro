# Markdown 内参照検証の設計 - checkRefs

本ドキュメントは、Markdown 本文中のリンク（`a href`）と画像（`img src`）をビルド時に検証する
機能の**設計判断とその理由**を記録するものである。`09_LINK_SAFETY.md` 5 章で「重要な穴」と
自認していた、`11_TODO.md` の課題 3 の設計にあたる。本書は設計段階のドキュメントであり、
実装後に使い方を `04_USAGE.md` へ追記する。

関連実装（予定）: `packages/cirrojs/src/markdown.tsx`（`createMarkdownProcessor` への組み込みと
`MarkdownConfig.checkRefs`）/ `registry/registry.ts`（`checkLink` / violation ストアの既存レール）。

---

## 1. 問題設定

ブログでは内部リンクの大半が Markdown 本文にあるのに、現状の検証対象は JSX の `<Link>` のみで
ある。リンク安全性という差別化機能が、最もリンクが多い場所をカバーしていない。画像も同様で、
`![](/images/foo.png)` の参照切れはビルドを通過して配信後に壊れる。

一方で、`09_LINK_SAFETY.md` の設計資産はほぼそのまま流用できる。

- `renderMarkdown()` はコンポーネント内＝ALS コンテキスト内で実行されるため、`checkLink()` と
  violation ストア（brokenLinks）のレールがそのまま使える。
- URL ストアは public 層（09 の 4.3）を既に持つため、`img src` の照合も同じ Set で済む。

## 2. 設計原則

> Markdown パイプラインの**信頼済み層（sanitize 後）**に組み込みの rehype プラグインを置き、
> `a href` と `img src` を既存の `checkLink()` レールで検証する。新しい正規化関数・報告機構は
> 一切作らない。`<Link>` との規則の差分は「スキーム付き URL は素通し」の 1 点のみとする。

- 検証対象は「実際に出力されるツリー」。sanitize 後に置くことで、利用者プラグインが生成した
  リンクも通り、sanitize が落とした属性を誤検証することもない。
- violation は既存の brokenLinks ストアへ収集し、報告も既存レール（dev は警告、build は
  ページ path 付きでまとめて非ゼロ終了）に乗せる。
- プラグインは公開せず `createMarkdownProcessor` の内部に組み込む。利用者が配線を間違え
  られない（sanitize を強制にしたのと同じ思想）。

## 3. 検討して不採用にした案

### 3.1 外部 URL を malformed にする（`<Link>` と同一規則。不採用）

`<Link>` が外部 URL を拒否できるのは「外部リンクは素の `<a>` で書く」という代替記法が
あるからである。Markdown 本文に代替記法はなく、外部リンクは自然に書かれる。よって
スキーム付き URL（`https:` / `mailto:` 等）は検証対象外として素通しする。
なお危険スキームの排除は本機能の責務ではなく、上流の `rehype-sanitize`（許可プロトコルの
allowlist）が既に担っている。

### 3.2 相対パスの解決を試みる（不採用）

`./foo` や `foo.html` を「現在ページの URL 基準で解決してから照合する」案。Cirro では
コンテンツ層が Markdown ファイルの置き場所と URL 構造を切り離しているため、相対リンクの
解決結果は**そのMarkdown がどのページで描画されたかに依存する**。同じ記事が `/blog/foo` と
`/index`（抜粋）の両方に出た場合、同じ相対リンクが別の場所を指し、静かに壊れる。
`<Link>` と同じく malformed として弾き、エラーメッセージに「ルート相対（`/` 始まり）で書く」
という解決方法を含める。

### 3.3 自サイトの絶対 URL の同一オリジン照合（初期フェーズでは見送り）

site 宣言（`12_SITE_METADATA.md`）があれば、`https://example.com/about` のようにベタ書き
された自サイト URL のオリジンを照合し、パス部分をストアで検証できる。しかし初期フェーズでは
**素通し**とする。

- 「スキーム付き＝素通し」という 1 行で説明できる規則のシンプルさを優先する。
- 素通しであることが、**ルート表にない同一ドメイン URL**（別システムが配信する `/app/...` 等）へ
  意図的にリンクするための逃げ道を兼ねる。
- 将来候補として残す（7 章）。

### 3.4 既定オフ（opt-in）にする（不採用）

`<Link>` の検証が opt-in なのは素の `<a>` という代替があり「Link を使えば守られる」という
契約が成立するからである。Markdown には記法の選択肢がなく、opt-in にすると誰も気づかない
まま穴が残り続ける。**既定オン**とする。既存サイトへの破壊的変更だが、利用者が限られている
現時点で移行する（CHANGELOG に記載）。

ただし完全強制（sanitize と同格）にはしない。リンク切れはセキュリティではなく品質の問題で
あり、オフスイッチ（`checkRefs: false`）は正当である。

### 3.5 プラグインを公開 API として export する（不採用）

利用者が `rehypePlugins` に自分で追加する形。sanitize より前のユーザープラグイン層に
置かれると検証対象が最終ツリーと一致しなくなり、置き場所を利用者の規律に委ねることになる。
組み込み + 設定フラグの方が誤配線の余地がない。

## 4. 採用した設計

### 4.1 分類ルール

プラグインは各 `a` の `href`・各 `img` の `src` について次の 1 判定だけを行う。

> **スキーム（`/^[a-z][a-z0-9+.-]*:/i`）で始まるものはスキップし、それ以外はそのまま
> 既存の `checkLink()` に渡す。**

結果として `<Link>` との対応は次のとおりになる。

| 参照の形 | `<Link>` | Markdown（本機能） |
| --- | --- | --- |
| `/about` などルート相対 | ストア照合 | 同じ（存在しなければ not-found） |
| `#section` アンカー | 素通し | 同じ |
| `https://...` 等スキーム付き | malformed | **素通し（検証対象外）** |
| `./foo`・`foo.html` 等相対パス | malformed | 同じ（3.2） |
| `//host/...` プロトコル相対 | malformed | 同じ |
| 不正な % シーケンス | malformed | 同じ |

- 相対パス・プロトコル相対・不正シーケンスの拒否、fragment / クエリの除去、
  `decodeURIComponent` はすべて `checkLink()` が既に行う（`09_LINK_SAFETY.md` 4.2）。
  本機能で新しい正規化は追加しない。
- `img src` の照合先も同じ URL ストアである。public 層（09 の 4.3）が含まれているため、
  `/images/foo.png` は public の実ファイルと照合される。

### 4.2 パイプライン上の位置

`createMarkdownProcessor` のパイプライン（ユーザープラグイン層 → `rehype-sanitize` →
信頼済み層）の**信頼済み層**に組み込む。ハイライト・toc と同格の位置である。

- sanitize 後なので、検証対象は実際に出力されるツリーと一致する。ユーザーの remark / rehype
  プラグインが生成したリンクも検証され、sanitize が除去した属性を誤検証することもない。
- raw HTML は `allowDangerousHtml` を渡していないため通らず（`04_USAGE.md` 7.2）、検証対象は
  Markdown 記法由来とプラグイン由来の要素に限られる。

### 4.3 violation の収集と報告

`checkLink()` の既存レールに乗せる。追加するのは violation レコードの出自情報のみ。

- レコードに **`href` / `src` の別と Markdown 由来であること**を含め、報告時に
  JSX の `<Link>` 起因と区別できるようにする（grep の当たり先が変わるため）。
- 報告は既存どおり: **dev はレンダリング完了後にコンソール警告、build は全ページ処理後に
  出力ページの path 付きでまとめて報告し非ゼロ終了**（`09_LINK_SAFETY.md` 4.5）。
- 帰属はページ単位で実用上十分（09 の 4.5 と同じ判断）。ブログではページ ≒ 記事 ≒
  Markdown ファイルなので、どのファイルかは実質特定できる。

### 4.4 公開 API: `MarkdownConfig.checkRefs`

```ts
createMarkdownProcessor({
    checkRefs: true, // 既定 true。a href と img src の検証。false で無効化
});
```

追加する公開 API はこのフラグ 1 つだけ。プラグイン本体は export しない（3.5）。

### 4.5 レンダリングコンテキスト外での挙動

loader 内での事前レンダリング（検索インデックス生成等）では ALS の Store が存在しない。
この場合、**検証をスキップして通常どおり描画する**（throw しない）。

- 「検証はページ描画時に行われる」ことを制約としてドキュメントに明記する。
- 同じ Markdown は通常のページ描画でも `renderMarkdown()` を通るため、検証漏れが
  実害になるケースはほぼない（ページに一度も描画されないMarkdown だけが漏れる）。

## 5. 制約と非目標

- **外部リンク・外部画像の死活確認はしない**（09 の 1 章と同じ。ビルドの決定性を守る）。
- **自サイトの絶対 URL は検証しない**（3.3。将来候補）。
- **fragment の存在検証はしない**（`/about#section` の `#section` が見出し id として存在するかは
  照合しない。09 の 5 章と同じ非目標）。
- **検証はページ描画時のみ**（4.5）。レンダリングコンテキスト外の `renderMarkdown()` は
  検証されない。
- **外部画像と CSP**: 推奨 CSP（`default-src 'self'`）では外部画像はブロックされる。Markdown に
  外部画像を書く場合は利用者が `img-src` を緩める必要がある（`10_IMAGE_ASSETS.md` 6 章と同じ
  注意。ドキュメントに明記する）。
- **`video` / `audio` / `source` 等の src は対象外**（そもそも sanitize の既定スキーマが
  通さない。スキーマを拡張して使う利用者は自己責任の領域である）。

## 6. 実装順序

1. プラグイン本体（信頼済み層への組み込み + 分類 1 判定 + `checkRefs` フラグ）
2. violation レコードへの出自情報（Markdown / href / src）の追加と報告文言の調整
3. examples/blog での確認（意図的なリンク切れを置いて build が落ちることのテスト）
4. `04_USAGE.md` 7 章・`09_LINK_SAFETY.md` 5〜6 章の記述更新

## 7. 将来の拡張候補

- **同一オリジン照合**（3.3）: site 宣言があるとき、`site.origin` と一致する絶対 URL の
  パス部分をストアで検証する。導入する場合、「ルート表にない同一ドメイン URL」の逃げ道が
  消えるため、opt-in フラグまたは除外指定とセットで検討する。
- **fragment の存在検証**: toc が見出し id を生成しているため、`/about#section` の照合は
  原理的に可能（09 の 6 章と同根）。
- **`<Link>` 側との出自統合レポート**: 違反件数が多いサイト向けに、出自（JSX / Markdown）
  ごとの集計表示。必要になったら検討する程度の優先度。
