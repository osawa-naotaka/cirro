# 画像アセットの設計 - Image / FaImage コンポーネント

本ドキュメントは、画像アセットの取り扱い（`<Image>` コンポーネントによるビルド時の存在検証・
コピー、および `<FaImage>` による Font Awesome アイコンのスプライト参照）の**設計判断とその理由**を
記録するものである。`09_LINK_SAFETY.md` 3.6 でペンディングとした `img src` 対応の設計にあたる。
本書は設計段階のドキュメントであり、実装後に使い方を `04_USAGE.md` へ追記する。

関連実装: `packages/cirrojs/src/lib/Image.tsx` / `lib/FaImage.tsx` /
`lib/fontawesome.ts`・`lib/fontawesome-{brands,regular,solid}.ts`（生成物）/
`script/genFontAwesomeDefs.ts`（生成スクリプト。`pnpm gen`）/ `registry/registry.ts`
（Link と同じ ALS Store のレール）/ `runtime/build.ts`・`runtime/dev.ts`・`runtime/router.ts`・
`runtime/icon.ts`。

**実装フェーズ**（2026-07 決定）: 利用頻度と実装の手間から、① 種別 2（public 照合）のみの
`<Image>`、② `<FaImage>` の順で実装する。種別 3・4（コピー機構・dev 配信ミドルウェア・realpath
検証を必要とする部分）は①②の完了後に必要性を再検討する。①の時点でも `from` の prefix 判別は
3 章の構文どおり実装し、種別 3・4 の形式は malformed とは区別して「未対応」として報告する
（将来の有効化を前方互換にするため）。

①・②は 2026-07 に実装済み。②は当初ビルド時のインライン SVG 展開としていたが、実装トライアルで
島のハイドレーションと両立しないことが判明し、**スプライト参照方式**（5.7）へ変更した（経緯は
4.7）。スプライトのサブセット化は行わず、まずはフルサイズのスプライトを使う（サブセット化は
7 章の将来候補）。

---

## 1. 問題設定

リンク切れと同様に、画像の参照切れも「ビルドは成功するのに配信後に壊れる」不具合であり、
ビルド時に検出できるはずである。ただし画像はリンクと違い、**参照検証だけでは完結しない**。
`public/` 外の画像（`src/` 内の画像や npm パッケージが同梱するアセット）は、検証に加えて
**`dist/` へのコピー**が必要になる。

### 1.1 なぜ Vite の asset import に任せられないか

Vite には `import imgUrl from "./foo.svg"` でハッシュ付き URL を得る標準機構があるが、Cirro では
機能しない。Cirro のページは一時 SSR サーバでレンダリングされるだけで**クライアントバンドルに
含まれない**ため、asset import は URL 文字列を返しても**実体ファイルが dist へ emit されない**
（emit はクライアントビルドの仕事であり、島のバンドルにはページの import は含まれない）。

したがって、Cirro 自身が明示的なコピー機構を持つことは必然である。これは「生成物を事後に
走査しない・利用者に仕組みが見える薄さを保つ」方針（09 の 3.2 と同根）とも整合する。

### 1.2 画像ソースの分類

画像の出どころは 4 種類に分類できる。

| 種別 | 例 | 検証 | コピー |
| --- | --- | --- | --- |
| 1. 外部サイト | `https://example.com/a.png` | しない（死活確認は不可能） | しない |
| 2. `public/` 配下 | ロゴ、OGP 画像 | 存在チェック | 不要（Vite が public をコピー） |
| 3. npm パッケージ同梱 | アイコン集・図版などのアセット | 存在チェック | dist へハッシュ付きコピー |
| 4. 自サイトのソース内 | `src/assets/` の図版 | 存在チェック | dist へハッシュ付きコピー |

なお Font Awesome は種別 3 の一般機構には乗せず、専用の `<FaImage>` で扱う（5.7）。

## 2. 設計原則

> 画像は `<Image from="...">` で宣言し、**レンダリング中に**、レンダリングと同じコンテキスト
> （AsyncLocalStorage の Store）で存在検証とコピー予約を行う。dev は警告、build はエラーとする。
> ソースの取り込みが必要なもの（種別 3・4）は、コンテンツハッシュ付きファイル名で `dist/assets/`
> へコピーする。

- Link（`09_LINK_SAFETY.md`）と同じレールに乗せる。「レンダリング中は Store へ積むだけ、
  warn / error の判断と報告はレンダリング後にランタイムが行う」パターンを踏襲する。
- チェック・コピーされるのは**実際にレンダリングされた画像だけ**である。
- 検証は opt-in である。素の `<img>` はチェックされない。外部画像（種別 1）は素の `<img>` で
  書く（Link が外部リンクを素の `<a>` に逃がしたのと同じ contract）。
- 種別 3・4 はファイルシステムへのアクセスを伴うため、**トラバーサル・symlink 越えを許さない**
  検証を build / dev で共有する（5.3 参照）。

## 3. `from` の構文

`from` は prefix で種別を判別する単一の文字列 prop とする。

| 書き方 | 種別 | 意味 |
| --- | --- | --- |
| `/images/logo.png` | 2 | `public/` 基準のルート相対パス |
| `@fortawesome/fontawesome-free:/svgs/solid/xmark.svg` | 3 | パッケージ名 + `:` + パッケージルート相対パス |
| `:/assets/figure.svg` | 4 | `assetDir`（既定 `src`）基準のパス |
| 上記以外（外部 URL・相対パス等） | — | **malformed** として報告 |

- `:` は区切りとして曖昧さがない。npm パッケージ名に `:` は使えず、スコープの `/` とも衝突しない。
- `/path`（public 照合のみ）と `:/path`（コピー + ハッシュ）は 1 文字差だが、書き間違いは
  どちらも「ファイルが存在しない」エラーで検出される（silent failure にならない）。エラー
  メッセージには「`/` 始まりは public 基準、`:/` 始まりは assetDir 基準」と両方の解釈を併記する。

## 4. 検討して不採用にした案

### 4.1 Vite の asset import に任せる（不採用）

1.1 のとおり、SSR 専用ページでは実体が emit されず成立しない。

### 4.2 プレースホルダ + post-render 置換（不採用）

レンダリング時は仮 URL を書いておき、レンダリング後にハッシュ確定と文字列置換を行う案。
生成物を事後に加工する方式は「利用者から魔法に見える」ため採用しない（09 の 3.2 で post-build
スキャンを不採用にしたのと同じ理由）。ハッシュはレンダリング中に同期的に確定できる（5.4）ので、
置換の必要自体がない。

### 4.3 dev で「レンダリング時に登録された URL のみ配信」（不採用）

dev サーバーの画像配信を「レンダリング中に登録された ハッシュ URL → 絶対パス のマップにある
ものだけ配信し、リクエストからのパス解決を一切しない」形にする案。LFI（任意ファイル読み出し）を
構造的に不可能にできるが、dev でもハッシュ計算が必要になり、URL がリクエスト順に依存する。

冷静に脅威モデルを整理すると、この強度は不要と判断した。

- LFI と呼ぶべきは `../` や symlink で**境界外**（プロジェクト外）へ到達できる実装であり、
  「リクエストからパス解決すること」自体ではない。build と同一のバリデータ（5.3）を通せば、
  読める集合は「assetDir 以下 + 直接依存パッケージ以下」に正確に閉じる。
- Vite の dev サーバーは元から `src/` 以下を HTTP で配信しており（transform / 静的配信
  ミドルウェア、`/@fs/` 経由の node_modules）、Cirro のミドルウェアが同じ範囲を配信可能に
  しても**dev 時の露出面は実質増えない**。

そこで dev は「ハッシュなし URL をリクエストから解決、ただし build と同一バリデータ +
Vite の `server.fs.deny` を通す」方式とした（5.6）。

### 4.4 外部 URL を Image で受ける（不採用）

利用者が全画像を 1 つのコンポーネントで書けるよう、`from` に `https://...` を許して素通しする案。
Link が「外部リンクは素の `<a>`」としたのと一貫させ、外部画像は素の `<img>` とする。
「Image を通したものは検証済み」という contract を濁さないためである。

### 4.5 Font Awesome: webfont 方式（不採用）

CSS クラス（`fa-solid fa-xmark`）+ webfont で使う方式。CSS が woff2 を相対 URL で参照するため、
CSS + フォント一式をパス関係を保って配布する別機構が必要になる。スプライトは自己完結した
1 ファイルのコピーで済むため、SVG（スプライト）方式のみとする。

### 4.6 Font Awesome: SVG を `<img>` でコピー配置（不採用）

FA の SVG を種別 3 の通常コピーで `<img src>` として使う案。外部ドキュメントの SVG には CSS の
`fill` が効かないため、**アイコンが黒一色に固定される**。アイコン用途では色の追従が実用上
不可欠なので、FaImage はインライン `<svg>` によるスプライト参照とする（5.7）。インライン SVG は
マークアップでありスクリプトではないため、CSP 厳格性（インラインスクリプトゼロ）は崩れない。

### 4.7 Font Awesome: ビルド時インライン展開 — readFile + dangerouslySetInnerHTML（不採用）

当初採用していた案。レンダリング中に SVG ファイルを `readFileSync` し、ルートタグを React で
再構成（`fill="currentColor"`・`height="1em"`・aria 属性を付与）、中身を
`dangerouslySetInnerHTML` で流し込む設計だった（fill の付与方法として CSS 配布・文字列への
字面挿入も比較検討し、ルートタグ再構成が最良と結論していた）。

しかし**実装トライアルで島と両立しないことが判明した**。

- 島は「ビルド時に SSR した初期 HTML を `hydrateRoot` で活かす」方式であり（`03_ISLAND_SYSTEM.md`）、
  サーバー HTML とクライアントが作る仮想 DOM の一致が契約である。
- `resolve` / `readFile` は Node 専用で、ブラウザは SVG の中身を再現できない。島内の FaImage は
  「動かない」ではなく **hydration mismatch として壊れる**。
- 問題の本質は「レンダリング時にファイルの**中身**を必要とすること」にある。中身ではなく
  **参照**を出力するスプライト方式（5.7）なら、サーバーとクライアントが同一のマークアップを
  自明に生成できる。

なお `<img src>` コピー（4.6）もこの問題自体は回避できるが色が固定される。hydration 一致と
色の追従を両立するのがスプライト参照である。

### 4.8 Font Awesome の別パッケージ分離（保留）

`@fortawesome/fontawesome-free` は SVG 数千個 + webfonts で unpacked 数十 MB 規模あり、cirrojs の
dependencies に入れると全利用者のインストールが重くなる。`@cirrojs/fontawesome` として分離する案も
あるが、**ゼロステップで使える利便性とシンプルさを優先し、まずは cirrojs の直接依存として同梱する**。
分離は利用状況を見て再検討する。なお dist に出力されるのはビルドで参照されたスタイルの
スプライトのみである（サイズの議論は 5.7・6 章）。

## 5. 採用した設計

### 5.1 Image の API

Link と同型の薄いラッパーとし、独自 prop は `from` のみ。`<img>` の標準属性（`alt` / `width` /
`height` / `loading` / `className` 等）は素通しする。

```tsx
export type ImageProps = Omit<ComponentPropsWithoutRef<"img">, "src"> & {
    from: string;
};

export function Image({ from, ...rest }: ImageProps): ReactNode {
    const src = checkImage(from); // 検証 + (種別3・4は)出力URLの確定
    return <img {...rest} src={src} />;
}
```

- **`src` は型から除外し `from` に一本化する**。Link の `to` と同じく、`{...rest}` を先に展開し
  `src` を後置することで、型を無視した `src` の混入を上書きする。
- Image は**コピーに徹する**。SVG のインライン展開は行わない（5.8 の信頼境界）。
- 画像最適化（リサイズ・srcset 生成・フォーマット変換）は**行わない**。Next.js の `<Image>` の
  ような最適化コンポーネントではなく、検証とコピーだけの薄いラッパーである（6 章）。

### 5.2 ソース種別ごとの処理

**種別 2（public）**: URL ストアの public 由来層（09 の 4.3。img src 検証の先行投資として構築済み）
と照合する。Link と同じく `decodeURIComponent` を通し、`?query` / `#fragment`（SVG スプライト等）は
照合時に除去する。出力は as-written。public は Vite 規約で「そのまま配信」なので、ハッシュ付与も
コピーもしない。

**種別 3（パッケージ）**: パッケージ名部分と パス部分を検証（5.3）し、パッケージルートからの
実ファイルを確認のうえ、build ではコピーを予約する。**サイトの直接依存のみ許可**し、プロジェクト
ルートの `node_modules/<pkg>` から解決する。

- `require.resolve()` はエントリポイントを返すうえ、アセット系パッケージは `exports` フィールドで
  `./package.json` すらブロックしていることがあり、Node 標準の resolve API は使えない。
  `node_modules/<pkg>` を直接引く。
- pnpm はルートに直接依存しか symlink を張らないため、「直接依存のみ」の制約は自然に強制され、
  hoisting への依存も消える。

**種別 4（自サイト）**: `CirroOptions.assetDir`（既定 `src`）基準で解決する。検証・コピーは
種別 3 と共通。基準を assetDir に限定するのは、プロジェクトルート基準にすると `.env` 等の
取り込み事故や、`:/public/...` と書いて public の画像がハッシュ付きで二重コピーされる混乱が
起きうるためである。

### 5.3 パス検証: 字句検証 + realpath 封じ込め（build / dev で共有）

種別 3・4 はファイルシステムに触れるため、二段構えで検証する。**この検証関数は 1 個に集約し、
build とdev ミドルウェアで共有する**（09 の 4.4「正規化は 1 関数に集約」と同じ原則。build と dev で
検証の強さが乖離するのが最も事故りやすい）。

1. **字句検証**（わかりやすいエラーを早く出すための層）
   - パッケージ名部分: npm の命名規則の正規表現で検証する。これだけでトラバーサル文字が入る
     余地がなくなる。
   - パス部分: `/` 始まりを強制。`..` / `.` セグメント、`\`、null バイト、制御文字、
     `?` / `#`（種別 3・4 はファイルパスであり URL ではない）を拒否。デコードは行わず字面で扱う。
2. **realpath 封じ込め**（実質的な保証の層）
   - 基準ディレクトリ（パッケージルート / assetDir）を `realpath` してから、解決したファイルも
     `realpath` し、前者のプレフィックスに収まることを確認する。
   - 字句検証だけでは不十分な理由は **symlink** である。pnpm の node_modules は symlink だらけで、
     パッケージ内部にパッケージ外を指す symlink が存在しうる。realpath 検査はこれを弾く。

コピー先のファイル名は `元のbasename.コンテンツハッシュ.拡張子`（Vite 風）とする。basename に
URL として問題のある文字が含まれる場合はサニタイズする（実装時に確定）。

### 5.4 ハッシュとコピーのタイミング: レンダリング中に URL 確定、レンダリング後にコピー

`renderToStaticMarkup` は同期であり、`<Image>` はレンダリング中に最終 URL を返す必要がある。

- **レンダリング中**: `readFileSync` + コンテンツハッシュで出力 URL（`/assets/name.abc123.svg`）を
  即confirm して emit し、同時に「コピー予約」（解決済み絶対パス → 出力名）を Store に積む。
  ハッシュは解決済みパスでメモ化し、同じ画像が何ページに出ても読み込みは 1 回で済ませる。
- **レンダリング後**: build ランタイムが予約を重複排除して `dist/assets/` へコピーする。

コンテンツハッシュの副次効果として、ビルド間でファイル名が安定し（キャッシュに優しい）、
同一内容のファイルはソースが違っても自然に 1 個へ重複排除される。

### 5.5 違反の収集と報告

Link と同一のパターン（09 の 4.5）。`checkImage()` は throw せず、違反
（`{ type: "not-found" | "malformed"; from: string }`）を Store へ積む。

- **dev**: レンダリング完了後にコンソール警告。
- **build**: 全ページ処理後に、出力ページの path 付きで全違反をまとめて報告し
  `process.exitCode = 1`。
- ファイルが存在しない場合もレンダリング自体は続行する（`src` は空にする等。build が
  失敗するので成果物が配信されることはない）。
- browser 側（島内）は Link と同じく no-op（09 の 4.6 と同じレール）。

### 5.6 dev サーバーでの配信

dev には dist がないため、種別 3・4 はミドルウェアで配信する。**dev ではハッシュをファイル名に
含めず**、`from` から機械的に導ける URL を使う（例: `/@cirro/asset/pkg/<pkgname>/<path>` と
`/@cirro/asset/site/<path>`。名前空間は Vite の `/@fs/` `/@id/` と同じ流儀で衝突しないものを切る。
正確な形式は実装時に確定）。build と dev で URL が違うことは、Image がレンダリング時に src を
確定させる設計なので利用者には見えない。

ミドルウェアは次を守る。

1. リクエストパスの解決に **5.3 と同一のバリデータ**を通す。これにより読める集合は
   「assetDir 以下 + 直接依存パッケージ以下」に閉じ、Vite dev が元から配信している範囲を超えない
   （4.3 参照）。
2. 解決後のパスを Vite の `isFileServingAllowed()`（`server.fs.deny`: `.env`・`.env.*`・
   `*.{crt,pem}`・`.git` 等）に通す。Cirro のミドルウェアが Vite 本体より弱い穴にならないため。
3. 存在検証と警告はレンダリング中の `checkImage()` が担い（5.5）、ミドルウェアは配信だけを行う。

### 5.7 FaImage: Font Awesome スプライトの `<use>` 参照

Font Awesome を「事実上のデフォルトのアイコン」として、利用者が `pnpm add` せずゼロステップで
使えるようにする。汎用 Image とは別コンポーネント `<FaImage>` とする。分離する理由:

- 汎用 Image の「**サイトの**直接依存のみ」ルールに穴を開けない。FA の実体（スプライト）は
  `createRequire(import.meta.url)` で **cirrojs 自身の依存**として `@fortawesome/fontawesome-free`
  を resolve する。pnpm の厳格な node_modules でも cirrojs 直下の symlink から確実に届き、
  利用者側の node_modules に hoist されている必要がない。
- **型の質が上がる**。cirrojs は FA を **exact pin**（`"7.3.0"`。`^` だと利用者の lockfile が
  範囲内の別バージョンを引き、生成済みの型と実体のスプライトが乖離し得る）で依存するため、
  アイコン名のリテラルユニオン型とメタデータ（後述）を事前生成して export できる。`icon` prop は
  `{ type: "solid", name: "xmark" }` 形式の判別可能ユニオン（`FaIcon`）で、スタイルごとに
  `name` のリテラルユニオンが効くため、補完が効き、存在しないアイコンは**コンパイル時に**
  弾ける。Link で見送った「型による静的チェック」（09 の 3.1）の鶏卵問題は、バージョン固定の
  同梱パッケージでは発生しない。

表現は**インライン `<svg>` + 同梱スプライトへの `<use>` 参照**とする（4.6・4.7 参照）。

```tsx
export type FaImageProps = ComponentPropsWithoutRef<"svg"> & {
    icon: FaIcon; // { type: "brands" | "solid" | "regular"; name: スタイルごとのリテラルユニオン }
};

export function FaImage({ icon, ...props }: FaImageProps): ReactNode {
    registerIcon(icon); // 存在チェック + 使用アイコンの収集（ALS Store のレール。5.7 末尾）
    const size = ...;   // 生成メタデータから viewBox の幅を引く
    return (
        <svg xmlns="http://www.w3.org/2000/svg" viewBox={`0 0 ${size} 512`} aria-hidden={true} height="1em" {...props}>
            <use href={`${faDir}/${icon.type}.svg#${icon.name}`} />
        </svg>
    );
}
```

- `aria-hidden`（装飾扱い）と `height="1em"`（周囲のテキストサイズに追従。viewBox のアスペクト比
  から幅が自動で決まる）はデフォルトとして `{...props}` の前に置き、利用者の props で上書き
  できる。意味を持たせる場合は `aria-hidden={false}` と `aria-label` / `role="img"` を渡す。
- **`fill` はコンポーネント側では付与しない**。FA スプライトの path 側に既に
  `fill="currentColor"` が付いており（後述）、色はそのまま周囲のテキスト色に追従する。
  ユーザー CSS での上書きも可能。
- URL は `faDir`（`"/fa"` 固定。`/fa/solid.svg` 等）から組み立てる。この値はクライアント
  バンドルにも入る（href はブラウザでも生成される）ため、サーバー側だけで解決される実行時
  オプションにはできない。設定可能にする場合は両環境へ同一値を配る仕組みが必要になるため、
  固定値とした。

これは**純粋なマークアップであり、レンダリング時に Node API もファイルの中身も必要としない**。
サーバーとクライアントが同一の仮想 DOM を自明に生成するため、静的部分でも島の中でも同じ実装が
動き、hydration も一致する（4.7 の問題の解）。`<use>` の外部参照はブラウザのネイティブ機能
なので JS に依存せず動き、CSP 厳格性も崩れない。

この方式を成立させている FA パッケージ側の事実（7.3.0 で確認）:

- `sprites/solid.svg`（856KB）・`regular.svg`（116KB）・`brands.svg`（580KB）が同梱され、
  各アイコンは `<symbol id="xmark" viewBox="0 0 448 512">` として格納されている。
- **path には既に `fill="currentColor"` が付いている**。属性の挿入も SVG の加工も一切不要で、
  ファイルを無加工でコピーするだけでよい。
- ファイル先頭に CC BY のライセンスコメントがあり、無加工コピーで帰属表示が保持される。
- viewBox は全アイコンが `0 0 W 512` 形式（W は 128〜640 の 9 種類）。したがって事前生成する
  メタデータは実質 `name → W` の数値 1 個で、リテラル型と合わせてクライアントバンドルに
  載せても小さい。サーバー側では `registerIcon()` がこのメタデータ（`allowed_icon_names`）と
  照合して存在チェックも行う（型を無視した JS 利用者向けの防衛。違反は `"not-exist"` として
  Image と同じレールで Store へ収集し、browser は no-op）。

**リテラル型とメタデータの生成元はスプライトの `<symbol>` そのものとする**。`svgs/` の
ファイル一覧を情報源にしてはならない。`svgs/` は正規名に加えて**旧名（エイリアス）の重複
コピーを含む**（7.3.0 で 3 スタイル計 720 ファイル。例: `ambulance.svg` は `truck-medical.svg`
とバイト同一）のに対し、スプライトの symbol は正規名のみを収録しており、ファイル名由来で
型を生成すると「型は通るのに symbol が存在しない」名前が生まれる（実装時にこの事故を確認
した）。配信する成果物自身を唯一の情報源にすることで、型と実体は原理的に乖離しない。型は
正規名のみのユニオンとなり、旧名はコンパイル時に弾かれる（FA 公式ドキュメントの現行名が
そのまま通る。旧名の受理は `metadata/icon-families.json` の `aliases` から対応表を生成すれば
将来可能だが、初期フェーズでは行わない）。

生成は `script/genFontAwesomeDefs.ts`（`pnpm gen`。biome format まで含むため再実行しても出力が
一致する）で行い、`lib/fontawesome-{brands,regular,solid}.ts` として `name → W` のマップ・
生成元 FA バージョン（`fontAwesomeVersion`）・AUTO-GENERATED ヘッダを出力してコミットする。
スクリプトは fail-loud である——パースできない `<symbol>` 行・512 以外の viewBox 高さ・
symbol 総数との不一致はすべて throw——ため、FA のフォーマット変更で「型から静かにアイコンが
消える」ことはない。FA の更新時はバージョンを上げて `pnpm gen` を再実行する。

配布は次のとおり。**初期フェーズではサブセット化せず、スタイル単位のフルサイズスプライトを
無加工でコピーする**（サブセット化は 7 章の将来候補）。

- **配信 URL は合成ルートとして表現する**。`expandRoutes()` が 3 スタイル分の
  `type: "fontawesome"` ルート（`/fa/{style}.svg`）を常に生成し、dev は他のルートと同じ経路で
  配信する（`render()` が cirrojs 自身の依存から該当スプライトを読む）。専用ミドルウェアを
  持ち込まず既存のルート機構に乗せた形で、配信対象は**既知の 3 URL 固定**・リクエスト由来の
  パス解決を伴わないため攻撃面は存在しない（4.3 で議論した LFI の懸念とは無縁）。
- **build**: レンダリング中に `registerIcon()` が使用アイコンを Registry（`registry.icon` の
  Set）へ登録し、全ページ処理後に `bundleIcon()`（`runtime/icon.ts`）が観測されたスタイルの
  スプライトを `dist/fa/` へコピーする。合成ルート自体は build では書き出さない。ブラウザが
  取得するのは参照されたファイルだけなので、ページの重さに乗るのは使ったスタイル分のみ。
- 合成ルートはリンク照合の URL 集合からは CSS ルートと同様に**除外する**（build は使用スタイル
  しかコピーしないため、含めると「チェックは通るのに配信されない URL」が生まれる。dev / build
  で同一のフィルタを適用し、判定の乖離を作らない）。
- 島が初期レンダリングで描かないアイコンを実行時に初めて使う場合、build の観測から漏れる。
  これは CSS のスタイル収集と同一の制約であり、解法も同じ——`styleSample()`
  （`05_STYLING.md` 7.3）でサンプルを申告すれば、`registerIcon()` もレンダリングと同じ
  コンテキストで走るため収集される（examples/blog の Disclosure が実例）。
- スプライトはページ間でキャッシュが効く（テキストなので gzip / brotli で大幅に縮む）。FA の
  バージョンは cirro のリリースに固定されるため、キャッシュ無効化は生成済みの
  `fontAwesomeVersion` からハッシュを導いてファイル名に付与する形で将来対応できる（7 章）。

### 5.8 信頼境界

スプライト方式の採用により、`dangerouslySetInnerHTML` も SVG の中身の加工も設計から消えた。
FaImage が出力するのは自前の `<svg><use>` マークアップだけであり、特権的な操作は「cirro 自身が
バージョン固定で依存する既知の 3 ファイルを無加工でコピー・配信する」ことに限られる。

汎用 Image は引き続き `<img>` コピーに徹し、SVG のインライン化は行わない。SVG は `<script>`・
イベントハンドラ属性・`<foreignObject>` を含みうるため、ユーザー提供・任意パッケージの SVG を
インライン化する機能を将来検討する場合は、サニタイズを含む信頼境界の再設計を前提とする。
cirro が面倒を見られる範囲（自身の固定依存）でのみ特別扱いを提供する、という線引きである。

## 6. 制約と非目標

- **素の `<img src>` は検証しない**。Image を使うことによる opt-in の検証である。
- **外部画像の死活確認はしない**（種別 1）。外部画像は素の `<img>` で書く。なお `04_USAGE.md`
  9 章の推奨 CSP（`default-src 'self'`）では外部画像はブロックされるため、使う場合は利用者が
  `img-src` を緩める必要がある（ドキュメントに明記する）。
- **画像最適化はしない**。リサイズ・srcset・フォーマット変換・遅延読み込みの自動付与は行わない。
  `loading="lazy"` 等は標準属性の素通しで利用者が書く。
- **Markdown 本文中の画像は現時点では検証しない**（Link と同じ穴。7 章）。
- **単一ファイルのコピーのみ**。CSS + フォントのような相対参照を持つアセット群の一括配布は
  扱わない（4.5）。
- **FA の webfont 方式は提供しない**。SVG スプライト（FaImage）のみ。
- **FA スプライトはフルサイズで配布する**（初期フェーズ）。solid で 856KB あるが、テキストで
  圧縮が効き、ページ間でキャッシュされる。サブセット化は将来候補（7 章）。
- **`<use>` の外部参照は同一オリジン限定**。スプライトは自サイトから配信するため問題に
  ならないが、CDN 等の別オリジンにアセットを逃がす構成とは両立しない。
- 種別 3・4 の `from` に `?query` / `#fragment` は書けない（ファイルパスであるため）。

## 7. 将来の拡張候補

- **Markdown 内画像の検証**: rehype プラグインで `<img>` の src を同じ `checkImage()` に通す。
  Link の Markdown 対応（09 の 6 章）と同じレールに乗る。
- **width / height の自動付与**: コピー時に画像寸法を読み取って `width` / `height` を自動で
  emit すれば、CLS（レイアウトシフト）をビルド時に潰せる。SSG ならではの機能として有望。
- **FA スプライトのサブセット化**: アイコン単位の収集（`registry.icon`）は実装済みなので、
  残るは build 時に使用アイコンの `<symbol>` だけを含むサブセットスプライトを生成する部分。
  初期レンダリングで描かれないアイコン（島がクリック後に出すもの等）は、`styleSample()`
  （`05_STYLING.md` 7.3）の既存レールでサンプルを申告すれば収集できる。スタイル収集と
  同じ制約・同じ解法に乗るため、新しい仕組みを持ち込まずに実現できる。
- **FA スプライトのキャッシュ無効化**: 生成済みの `fontAwesomeVersion` からハッシュを導き、
  スプライトのファイル名に付与する（レンダリング時の計算はゼロのまま）。
- **`@cirrojs/fontawesome` への分離**（4.8 の再検討）。
- **SVG スプライト対応**: 種別 3・4 での `#fragment` 許可。
- **`from` の型強化**: 種別 2 に限り public ファイル一覧からのリテラル型生成（Link の
  静的ルート型化と同じ将来候補）。
